# RAM and CPU footprint audit

Research date: 2026-11-09. Independent inspection of the **dirty working tree**, based on HEAD `9447d0b9acf43f25da79439d33b17e009b0c359c`, including the ongoing native UI, AV1, decoder, portable and network-test edits. HEAD alone does not reproduce this source. Files were changing concurrently; links identify the inspected functions, and line positions may move. No application code, dependencies, manifests, locks, existing reports, branches or PRs were changed by this audit.

**Best practical starting point:** remove the portable launcher's payload-sized allocation from its waiting lifetime; avoid unchanged UI/preview copies and repeated subscription requests; then make image conversion follow actual presentation demand. These have narrower scope than replacing the renderer, audio backend or media SDK. The strongest active CPU hypothesis remains the full-frame receive conversion pipeline, overlapping the earlier [performance opportunities](performance-opportunities.md). The new findings below supplement that report rather than claiming a second independent measurement of its proposals.

**Evidence limit:** this is source-backed research, not a benchmark. No app, capture, audio, browser or network fixture was launched, no profiler was installed, and no existing process was sampled or disturbed. No secrets, room databases, saved profiles, private logs or process command lines were read. Hardware supplied by the task is Ryzen 7 9800X3D / RTX 5080; this audit establishes neither its actual resource use nor NVIDIA/AMD acceptance. There are no measured savings or speculative MB/percentage gains here.

## Version and measurement basis

The [workspace release profile](../../Cargo.toml) already enables thin LTO and `codegen-units = 1`. [Native dependencies](../../apps/publisher/Cargo.toml) and [Cargo.lock](../../Cargo.lock) select eframe/egui/epaint/glow 0.37.0, LiveKit 0.10.1, libwebrtc 0.4.0, Tokio 1.54.1, reqwest 0.12.28 and image 0.25.10; the [portable crate](../../apps/portable/Cargo.toml) uses zip 9.5.0. These build settings and archive compression do not establish resident memory savings.

The local runtime is task-specified GStreamer **1.28.8+git**. Its [distribution manifest](../../deploy/portable-runtime.json) records source commit `202e42fa1bbff4ed61e08d47202db5c744987f0c`. [SDK](../../deploy/native-sdk.json) and [decoder](../../deploy/native-decoder.json) manifests identify checksum-pinned generated-source inputs; inspected local SDK crates identify upstream Rust SDK commit `88705b15086ecbe2c26ee91ede6203f974a0fc62`. The installed `webrtc-sys-build` 0.3.21 source names prebuilt tag `webrtc-a545de4`; its [upstream build source][sdk-build] and [WebRTC decoder source at that revision][dav1d] support the CPU-decoder discussion. This is the source/default download lineage, not an attestation of a running binary or a custom WebRTC build. Upstream links use those revisions or the egui 0.37.0 release; matching local package source was inspected where public version pages were unavailable.

Use these separate resource accounts:

- **Working set:** currently resident process pages, including private and shared pages. DLL code and system DLL pages can be shared; summing process working sets double-counts shared pages. See Microsoft's [working-set definition][working-set].
- **Private bytes / process commit:** private committed memory, which need not all be resident. `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage` and its peak commit counterpart are defined in [Microsoft's counters reference][memory-counters]. Also record system commit to reveal pressure outside the app.
- **GPU memory:** record local/nonlocal usage and budget separately from CPU memory. [DXGI memory queries][gpu-memory] expose process usage and budget. Driver allocations, decoder surfaces and GL textures cannot be inferred from a Rust heap profile alone.
- **Allocation traffic and peaks:** count allocated bytes/second, allocation sizes, live/high-water bytes and time to release them. Fewer allocations may help CPU without lowering steady private bytes; a pool may reduce allocation traffic while increasing retained RAM. A smaller executable/archive/plugin directory is distribution evidence, not a resident-memory measurement.

## Native idle UI and invisible work

### Avoid work before an unchanged-value check

[`Controller::snapshot`](../../apps/publisher/src/publisher.rs) clones a `Snapshot` containing source/encoder/application vectors, participant strings, tile strings and metric structs. The frame pictures and atomics are `Arc` clones, **not deep pixel copies**. [`PublisherUi::ui`](../../apps/publisher/src/ui.rs) requests 250 ms refreshes when idle, 50 ms while busy and 16 ms while watching. Use revisioned `Arc` collections or a shared immutable snapshot so each paint takes a cheap stable view; replace collections when they change. Avoid holding the controller lock through egui layout. The worker independently rebuilds participants/tiles every 500 ms, so event-assisted reconciliation plus the existing timed health/budget checks is a further option after allocation profiling. These observations do not establish that UI strings dominate active media cost.

[`source_preview`](../../apps/publisher/src/ui.rs) clones `Option<Frame>` from the JPEG cache **before** checking `self_preview_revision`; [`Frame`](../../apps/publisher/src/preview.rs) derives `Clone` over a `Vec<u8>`. Therefore every invocation while a cached preview exists copies the JPEG even when its sequence is unchanged. The current UI places this in an expandable Source preview panel, so this churn applies when that panel is drawn, not every hidden/collapsed frame. Compare cache identity/sequence under the lock, and clone/share bytes only for a new revision. Retain the current `Arc` identity check across source changes; sequence numbers restart. Do not remove the once-per-minute capture gate.

The connected UI also constructs/validates [`Profile::new`](../../apps/publisher/src/settings.rs) before comparing the result with `attempted_profile`. That trims/copies strings and parses the invitation during unchanged UI updates; the store is saved only when the value changes, so **this is not evidence of disk writes every frame**. Move the candidate-value work to input/join changes while preserving validation before actual save. Avatar initials, metric formatting and selected labels are smaller candidates only if profiles show them; the [locale catalog](../../apps/publisher/src/locale.rs) is already initialized once and returns borrowed strings.

### Fullscreen and minimized are different lifecycle cases

Fullscreen calls `fullscreen_view` and returns **before** `textures.retain`, `remembered_volume.retain` and self-preview cleanup in [`PublisherUi::ui`](../../apps/publisher/src/ui.rs). Images uploaded for other tiles can remain in the texture map after those publishers depart while the selected fullscreen stream continues. This is delayed cache cleanup, not proof of an indefinitely growing pixel leak: normal cleanup resumes after leaving fullscreen, and that view does not create textures for newly unseen tiles. Move maintenance ahead of the return and release stale-generation textures even when layout is skipped. [TextureHandle ownership][texture-handle] schedules release when its last handle drops; the [glow backend][glow] performs the GL deletion during texture processing.

**Refinement to the earlier report's visibility caveat:** [egui 0.37 `ViewportInfo::visible`][viewport] already returns false for reported minimization or occlusion. Unknown state remains unknown; the app conservatively treats it as visible. More significantly, [eframe's pinned glow integration][eframe-glow] can skip `App::ui` altogether for a hidden viewport and call `App::logic` instead. FreedomStream implements only `ui`, so a future presentation-demand signal must be updated through `logic`/viewport events as well as layout; setting it only inside `ui` can leave stale visible demand after minimize. Verify actual Windows minimize/occlusion/restore events rather than claiming a 250 ms hidden UI paint rate from the app's conditional alone.

Fullscreen already uploads/renders the selected tile only. Independent receive pumps nevertheless continue converting every selected stream. Minimized rendering likewise does not stop those pumps. Stop **conversion/upload** for confirmed unpresented tiles while retaining actual subscriptions, decoding/receive health and audio. Restore must request a fresh image promptly. In [`Playback::reconcile`](../../apps/publisher/src/playback.rs), the six-second compatibility fallback uses `last_frame`, currently updated after conversion; update receive/decode liveness before any new presentation gate or hidden tiles could spuriously request a shared H.264 switch. This overlaps earlier performance candidate 2.

## Frame, surface and cache ownership

The inspected receive chain is [`Decoder::Configure/Receive`](../../apps/publisher/decoder/freedomstream_decoder.h): hardware decode → GPU download → I420 conversion → newly allocated/copied WebRTC I420 buffer; then [`Playback::reconcile`](../../apps/publisher/src/playback.rs): newly allocated RGBA bytes → separately constructed `ColorImage` → latest-picture slot → egui delta → GL upload. [epaint's image source][color-image] confirms `from_rgba_unmultiplied` builds another pixel vector, and [glow][glow] uploads that pixel data. Hardware decode does not make this a GPU-resident display path.

For tightly packed even-sized 8-bit images, I420/NV12 pixel payload is `1.5 × width × height`; RGBA/`Color32` payload is `4 × width × height`. Strides, alignment, reference frames, metadata and drivers add storage. These formulas describe payloads, not measured process use. Several stages can coexist: current conversion, a pending SDK frame, previous/new completed images, texture deltas and GPU textures. Do not multiply one frame size by one queue length and call it the application's peak memory.

Small/medium opportunities, in order:

1. Write conversion into exclusively owned `ColorImage::as_raw_mut()` storage instead of an intermediate RGBA vector, with full-write/stride/alpha/color fixtures. The pinned [image API][color-image] gates the raw view behind `bytemuck`, enabled by the current glow dependency. Recover an overwritten but unpresented image for reuse only when ownership is exclusive. Never mutate an image still held by an `Arc` texture delta. This is the earlier report's candidate 1, not a new zero-copy implementation.
2. Keep at most one pending decoded frame, one in-flight conversion and one completed picture per subscription, and bound total conversion concurrency. Retain no historical full-size images. Capacity one in the [SDK stream queue][video-stream] already discards old pending frames; it cannot undo conversions that the consumer has already started. Track received/converted/superseded/presented counts separately.
3. Try equal-size `set_partial([0, 0], image, ...)` after allocating the texture, with full `set` on geometry changes. [The handle API][texture-handle] and [glow source][glow] distinguish subimage upload from full image specification. Both transfer all pixels for a full-frame update; a driver allocation or RAM reduction is an experiment, not guaranteed by the method name.
4. Inspect unused `enable-last-sample` references on decoder output and the capture/preview/PCM appsinks. None of these application paths reads that property. The pinned [GStreamer basesink source][base-sink] enables it by default and supports disabling it to release the extra reference. Other queue/preroll/decoder references may still keep the same buffer alive; measure rather than subtracting a frame from a spreadsheet.
5. Only if allocation traces justify it, replace the adapter's per-frame `I420Buffer::Create` with a **bounded** [WebRTC `VideoFrameBufferPool`][frame-pool]. Its default constructor is effectively unbounded; reuse requires sole ownership, and exhausted bounded pools can return null. Set an explicit limit, handle exhaustion without corrupting frames, and release/reset on codec/size/generation changes. Pooling may increase retained RAM, so compare CPU traffic and private-byte/VRAM plateaus separately.

The [pinned D3D11 decoder][d3d11-decoder] maintains internal/reference and downstream pool accounting. `appsink max-buffers=2` is not a total decoder-surface cap. Required reference pictures and alignment are legitimate retention; blindly reducing decoder surfaces can stall decode. The custom input guard already rejects an input over 4 MiB or a push when queued bytes exceed 4 MiB; one accepted input can overshoot the threshold. `max-bytes` with `block=false` alone is a full-queue notification, not a hard bound ([bundled appsrc][app-src]). Frame/age limits and keyframe-safe recovery remain the earlier report's candidate 3; do not drop arbitrary compressed reference frames or treat the 128-entry timestamp map as a surface bound.

[`Playback`](../../apps/publisher/src/playback.rs) retains latest previews by participant while that publisher is live, including a prior preview entry after Watch starts. Usually `update_picture` has already taken its pixels, leaving an empty slot; an unpainted/offscreen preview can still retain a decoded `ColorImage`. Prune or demote such entries when live playback owns the tile, provided Stop watching still refetches the existing authenticated revision without requesting a capture. `suspend` clears pumps/previews/stat history but intentionally retains watch intent and its last picture; consider clearing stale picture/error generations without clearing user intent. Received-stat entries already prune against current keys every sample. These are cache-policy questions, not evidence that every preview retains both CPU pixels and a separate GL texture indefinitely.

## Control traffic, runtimes, worker counts and wakeups

### Coalesce subscription intent at the application boundary

Every 500 ms reconciliation calls `set_subscribed(enabled)` for each screen video/audio publication, including repeated false settings for unwatched streams and orphan audio. In the [pinned SDK setter][remote-publication], unchanged values still invoke `subscription_update_needed`; the [participant handler][remote-participant] spawns a task and sends a subscription signaling request. There is no unchanged-value guard at that setter/handler seam. Thus an unwatched but populated room has avoidable task/message construction even with no media pumps.

Keep applied desired state per **publication SID and room/recovery generation**, with a deliberately reasserted state on reconnect/replacement or failed application. `is_subscribed()` means a track exists; use desired-state semantics rather than retrying `true` every tick until a track appears. Preserve retry/error handling and clear entries on unpublish/leave. The existing attribute `announce != announced || announce_dirty` check already coalesces watcher codec/budget announcements; extend that discipline, not subscription semantics. Count requests at the SDK boundary and actual transport before asserting packet-rate savings.

The Tokio CPU-count behavior and ten-second blocking-thread retirement above were also checked directly in the pinned [CPU helper][tokio-cpus] and [blocking pool][tokio-pool]. Neither is evidence of this machine's effective runtime settings or measured idle wakeups.

Multiple Tokio builders in [`main.rs`](../../apps/publisher/src/main.rs) are mutually exclusive CLI fixture modes, not several concurrent GUI runtimes. The GUI's async SDK work uses Tokio tasks in the existing runtime; WebRTC's `RtcRuntime` is a different native thread owner. Likewise [`Admission`](../../apps/publisher/src/admission.rs) creates one reqwest client per admission and clones it for probes/previews/leave. [reqwest's pinned client][http-client] shares its pool through `Arc`; a clone is not another HTTP connection pool/runtime. Do not replace per-admission cookie isolation with a global shared authority jar to save allocations.

[`decoder_codecs`](../../apps/publisher/src/playback.rs) constructs a temporary `PeerConnectionFactory::default()` to query capabilities. [The pinned implementation][pc-factory] creates a factory rather than fetching the room's shared one. `Playback::new` runs at worker startup and on join/leave/recovery paths, so capability queries can create/destroy additional native runtimes and synthetic-ADM queues transiently. Cache the small capability result with explicit device/runtime invalidation, or query an SDK-owned factory through a supported seam. Do not retain an entire otherwise-unused factory just to retain a string list. This targets startup/rejoin churn, not proof of duplicate persistent media runtimes.

After moving heavy conversion out of async tasks, compare explicit small Tokio worker counts against the current default. Keep persistent CPU conversion on a bounded dedicated pool, not unlimited per-frame `spawn_blocking` jobs; [Tokio's pinned guidance][tokio-blocking] describes async starvation and the fact that started blocking jobs cannot be aborted. Preserve cooperative cancellation, generation checks and prompt join/leave/audio response. Do not shrink stacks, cap the blocking pool below long-lived jobs plus required service work, or force a current-thread runtime without evidence. Fewer threads can reduce reserve/commit or contention but can also worsen deadlines; parked threads do not prove material CPU cost.

Two lower-priority SDK checks deserve a soak/profile before patching: [the RTC wrapper registry][rtc-runtime] appends weak track references and does not prune expired entries in the inspected lookup, allowing small metadata/control-block accumulation through repeated track churn while the runtime lives; weak entries do **not** establish retained frames/decoders. Also the local WebRTC log bridge registers verbose callbacks and constructs FFI strings before Rust debug filtering; profile callback counts without recording messages before considering an earlier severity gate. Keep the application's sanitized diagnostics contract ([logger](../../apps/publisher/src/diagnostics.rs)).

## Software AV1 aggregate CPU policy

This audit advances the earlier report's candidate 5 beyond generic dav1d defaults. At the SDK's default WebRTC source revision, [dav1d `Configure`][dav1d] explicitly sets `n_threads = clamp(settings.number_of_cores(), 1, DAV1D_MAX_THREADS)` and `max_frame_delay = 1`; it does not simply inherit the library's auto-threading default. [WebRTC's receive stream][receive-stream] supplies the core setting. Four decoder instances can each request their own thread budget; no aggregate app budget appears in [`DecoderFactory`/playback](../../apps/publisher/decoder/freedomstream_decoder.h). Exact configured core values, OS threads and runnable parallelism still require instrumentation of the actual build. Do not report four times the CPU's nominal core count as a measured thread count.

If software decode is material while gaming, expose a narrow SDK decoder policy for **aggregate** CPU decoding/conversion capacity; compare per-decoder limits and fair admission/deadline handling at fixed source geometry/FPS/bitrate. `max_frame_delay` is already one; recommending a generic reduction from an assumed default would be wrong. Preserve grain/color/quality behavior and the existing one-publication compatibility contract. Lower thread counts can miss decode deadlines and build latency. In addition, dav1d [wraps output pictures with reference-counted lifetime][dav1d], so stale pending decoded-frame references can prolong decoder picture storage; close generation mailboxes promptly. Actual NVIDIA and AMD hardware/software paths must be identified independently rather than inferred from advertised AV1 support.

## Audio and discovery

[`playback::audio`](../../apps/publisher/src/playback.rs) owns one `appsrc → queue → audioconvert → audioresample → volume → wasapi2sink` pipeline per watched audio track. It reads the bus, polls queue properties, locks/scans scalar metrics, writes the gain property and allocates/converts PCM bytes for each delivered frame. The [SDK sink][audio-stream] already copies callback samples into owned `AudioFrame` storage. Small first steps: write gain only when the atomic value changes; aggregate peaks/queue telemetry locally and publish at UI cadence; acquire bus/control handles once; evaluate transferring an owned byte-compatible buffer or a bounded buffer pool with correct asynchronous GStreamer ownership. Do not reuse memory immediately after `push_buffer` or add unsafe borrowed storage to an async queue. Keep error detection and overrun guards effective; spectral metering is already diagnostic-only.

The existing five-frame SDK queue, 38,400-byte appsrc threshold/explicit pre-push guard and 100 ms downstream queue are bounded control points. At stereo S16/48 kHz, 38,400 bytes corresponds to 200 ms of PCM by arithmetic; it is **not measured total device or A/V latency**. Capture already uses a 50 ms SDK source queue, bounded appsinks/branch queues and clears source audio on pipeline replacement. Reducing these limits blindly may create underruns. Shared playout with one output device remains a larger comparison from the earlier report's candidate 6, with per-track volume/mute, device clock/delay, hotplug and exclusion acceptance; it does not by itself fix sync.

[`audio::Pipeline`](../../apps/publisher/src/audio/mod.rs) mixes an always-live silent source with up to 16 approved process-tree loopbacks, each with conversion/resampling/queueing. A single-root bypass or less mixer scheduling is optional only after the small playback fixes are measured, and must preserve silence, process-restart handling, fixed stereo format and transport timing. Do not accidentally publish one silent audio source per root or acquire microphone/default desktop loopback as a shortcut.

Display/window source enumeration occurs at worker startup, explicit Refresh and start/apply validation, **not** every 500 ms idle tick ([worker](../../apps/publisher/src/publisher.rs)). Audio capture does refresh [`windows::inventory`](../../apps/publisher/src/audio/windows.rs) every 500 ms: process snapshot, identity/image queries, then active render endpoint/session enumeration. This is active capture work, not a disconnected-idle poll. Event-assisted cached discovery overlaps earlier candidate 7. Preserve PID plus creation time, handle leases, parent ordering, unknown-identity rejection and protected descendants in [audio policy](../../apps/publisher/src/audio/policy.rs); callbacks are hints, not permission to lengthen the fail-closed revalidation window. Share only identity-stable information and revalidate before opening/replacing loopbacks.

## Portable distribution versus native process memory

[`Bundle::read`](../../apps/portable/src/lib.rs) reads and hashes the entire appended ZIP into `Bundle.bytes` before [`prepare`](../../apps/portable/src/lib.rs) checks the warm extraction cache. [`run`](../../apps/portable/src/main.rs) keeps `bundle` in its scope while `run_publisher` waits for the child. Thus compressed payload size `S` is a source-visible live heap allocation in the wrapper's waiting lifetime, including warm launches. It is not the uncompressed runtime size, and an allocator/OS need not immediately reduce working set or commit by exactly `S` after free. First make ownership end explicitly after preparation; then stream verification and ZIP extraction from a bounded seekable payload view to address the initial peak too. Streaming still needs checksum I/O; this is not a promise to eliminate warm-launch hashing CPU/time.

Preserve archive/footer verification, file/count/expanded-size limits, path/link defenses, extraction lock and atomic completion, required-file checks, hidden GUI launch and kernel-established lifetime job. The wrapper must continue supervising the child. Do not skip verification merely because the cache exists. Simultaneous launches currently serialize extraction only after each has read its own payload, another peak-memory test case. Notices and corresponding sources remain accessible, and cached LGPL libraries remain replaceable under the current distribution design ([portable code](../../apps/portable/src/lib.rs), [runtime qualification](../../scripts/portable-runtime.mjs)).

The [runtime manifest](../../deploy/portable-runtime.json) already curates DLLs/plugins rather than bundling all GStreamer. Further remove files only after import closure, registry/plugin loading and real H.264/HEVC/AV1, NVIDIA/AMD, capture, audio, offline/fresh-machine tests demonstrate they are unnecessary. Removing an unloaded test/tool/plugin DLL primarily changes disk/download/extraction work; loaded image pages are not all private committed RAM. Source/notices are distribution obligations, not expendable resident media buffers. Executable compression, more LTO, removing debug data and changing `codegen-units` again are not first-line runtime-footprint proposals.

## Server and web opportunities, separately

These do not shrink the native process. Prioritize them when API/SFU/proxy CPU or VPS pressure is observed.

- **Probe queries before probe buffers.** The current [server](../../apps/server/src/network-test.ts) streams one reusable 64 KiB download block; [native upload](../../apps/publisher/src/admission.rs) emits fresh bounded 64 KiB chunks, and download consumes chunks without collecting the full body. The 48 MiB negotiated limit is a transfer cap, not a 48 MiB eagerly allocated buffer per join. Server upload also streams. One shared lease, bounded duration/rate/maps and client abort/lease cleanup already restrict concurrent joins. Reuse an immutable upload `Bytes` block if allocation profiles justify it, and jitter busy retries if several friends synchronize; preserve test rate/bytes/duration and cancellation. Do not run probes in parallel or cache stale capacity indefinitely to hide their cost.
- **Repeated synchronous authentication work.** Both transfer loops call `rooms.session` per chunk. [`session/find`](../../apps/server/src/rooms.ts) hash the cookie, prepare SQL and query the room/session repeatedly. [Node 24's SQLite API][node-sqlite] is synchronous and prepared statements can be reused. Cache the small fixed set of prepared statements, not authentication results; use a narrower scalar validity query if it preserves precisely the same room/session/expiry/revocation contract. Measure query count/time, event-loop delay and stream throughput. Removing or stretching per-chunk identity revalidation is outside this recommendation. Hoisting only request-local constants and repeated non-authority work is safe scope; positive auth caching is a different correctness/security change.
- **Previews are bounded, not preallocated to their cap.** [`Previews`](../../apps/server/src/previews.ts) allows 256 compressed latest entries, 16 pending jobs, 256 KiB per upload and three-minute expiry ([contracts](../../packages/contracts/src/index.ts)). The 64 MiB maximum compressed-entry arithmetic is not idle RAM and excludes pending request, response and runtime overhead. Stop nulls image bytes while retaining a bounded cadence descriptor; owner removal and sweep release entries. Reuse existing buffers, measure actual occupancy/GC/external memory and tune capacity only to a demonstrated workload. Keep the minute anti-reset descriptor and live-publication proof. Collapse identical concurrent SFU participant lookups only if fresh post-await membership/publication checks and cancellation semantics remain intact ([media directory](../../apps/server/src/media.ts)); do not replace them with stale positive caches.
- **No whole-release file read to remove.** [`loadPublisher`](../../apps/server/src/distribution.ts) streams the EXE into a startup hash and serves it with `createReadStream`; only the small JSON manifest is read whole. Avoid a new in-memory EXE cache. The [production compose](../../deploy/production/compose.yaml) already sets Node heap/container and SFU memory bounds; smaller heap/`GOMEMLIMIT` settings can increase GC and packet-delay pressure and need server measurements, not a generic claim that limits save RAM.
- **The current website is admission/download UI.** [`App`](../../apps/web/src/App.tsx) imports room access and download components, not `MediaRoom`/`LiveStreams`; the older media modules' timers are not evidence of active production browser media work. Session validation currently polls every 20 seconds with a pending guard and cleanup; release metadata loads once per room. Native streaming does not embed a browser. Any remaining bundle/tree-shaking change is chiefly distribution/startup work until the actual served module graph and browser heap show otherwise. Preserve session revalidation and secret handling. Reducing browser media work that is no longer mounted is not a meaningful native RAM optimization.

The GC/limit tradeoff above follows the [Node 24 heap-limit documentation][node-heap] and [Go GC memory-limit guidance][go-gc]. Container limits, managed heap limits and total resident/private memory are distinct; lowering a configured ceiling is not proof that the same workload consumes less CPU or safely fits less RAM.

## Already optimized paths and ideas to avoid

Preserve these current contracts and optimizations:

- GPU-memory capture/scale/encode, one preencoded non-simulcast publication, bounded capture queues, effective-value-only bitrate writes and coalesced AMF reconfiguration ([encoding](../../apps/publisher/src/encoding.rs), [publication](../../apps/publisher/src/publisher.rs), [quality policy](../../apps/publisher/src/quality.rs)).
- Preview capture once at start, then at least 60 seconds apart, with the gate **before GPU scaling/download/JPEG encode**. Latest stills are reused; join, focus and retries must not increase capture cadence ([gate/upload](../../apps/publisher/src/preview.rs), [probe placement](../../apps/publisher/src/encoding.rs)).
- Capacity-one decoded video queues, capacity-five decoded audio queues, latest-picture replacement, ownership-taking UI upload, statistics-key pruning, pump abort-on-drop and SDK sink removal/queue close on stream drop ([playback](../../apps/publisher/src/playback.rs), [SDK video][video-stream], [SDK audio][audio-stream]). These bound particular stages; they do not prove that complete stop/rejoin releases all resources synchronously.
- Auto-subscribe disabled and explicit Watch/Stop watching calls; shared receiver allowance and compatibility fallback; admission-client pool reuse; atomic bounded cache extraction ([connection](../../apps/publisher/src/connection.rs), [playback](../../apps/publisher/src/playback.rs), [admission](../../apps/publisher/src/admission.rs), [portable](../../apps/portable/src/lib.rs)).

Avoid lower-value or unsafe shortcuts: forced working-set trimming/allocator purges to improve a Task Manager screenshot; assuming compressed EXE size equals RAM; unbounded reusable frame pools; decoding only keyframes; arbitrary leaky compressed queues; unbounded per-frame blocking jobs; globally reducing thread counts without deadline tests; repeated capability factories kept alive for caching; disabling authentication/discovery revalidation; reducing quality/geometry/FPS/bitrate silently; hidden unsubscribe or stopping other subscriptions in fullscreen; removing static-scene `imagefreeze` without late-join/keyframe proof; server transcoding, duplicate publications, default microphone acquisition or broad desktop-audio fallback. A D3D11 texture bridge or shared playout backend is a large design change already covered by earlier candidates 8/6, not a small packaging or framework toggle.

Distinguish leaks from intended retention using lifetimes: a stable warmed font/GL/decoder/allocator cache is not a leak merely because working set stays high after one stop. Repeated monotonically increasing **live** objects/private commit after identical cycles and a fixed settle period is stronger evidence; track textures, frame references, pipelines, SDK sinks, pending jobs, handles and weak-registry entries to identify the owner. A bounded last picture is intentional stale-image retention until its policy says otherwise. No runtime leak was established here.

## Proposed repeatable benchmark matrix

**This procedure was not run.** First add sanitized aggregate counters without payloads, invitations, session/media tokens, process command lines or raw SDP. For each build record source/patch identity, release profile, dependency/runtime/portable hashes, actual decoder/encoder backend and adapter, driver/Windows version, power/display/thermal state and fixed source geometry/FPS/bitrate/content. Record `TOKIO_WORKER_THREADS`' effective count without dumping environment variables. Use the same release artifact and seeded content for A/B; do not compare debug to release or different source targets.

Start with known-size moving and static synthetic fixtures and the existing [flash/click fixture specification](../verification/av-sync-fixture.md). Run a warm-up, then repeated fixed-duration samples; use at least five matched runs, a 60-second warm-up and a five-minute steady interval as an initial reproducible protocol. Use a fixed settle interval longer than the pinned ten-second blocking-thread retirement when comparing stopped states. Track peaks from process creation, not only after warm-up. Add a 30–60 minute churn soak after the short cases. Longer field sessions remain separate acceptance.

| Case | Controlled workload | What it resolves |
| --- | --- | --- |
| Portable startup | Cold private cache and warm cache; one launch and simultaneous launches; normal portable versus prepared native child under the same environment | Wrapper/child peak and lifetime ownership, hashing/extraction CPU/I/O, startup-to-usable UI |
| Idle | Disconnected app, then connected empty room; record initial automatic probe separately, then steady state with no capture/subscriptions | UI/control polls, worker/timer baseline, settled private/working-set/commit and persistent threads |
| Share alone | Fixed moving and static source, no watchers, source-preview panel open/closed | Encoder/capture/audio baseline and unchanged JPEG/snapshot churn; initial/minute preview capture counts |
| Watch | One publisher, then four actual watched publications; H.264/HEVC/AV1 hardware plus explicitly forced software AV1 | Decode/conversion/audio scaling, aggregate threading and memory plateaus |
| Publish plus watch | Share while receiving one/four publications, with one/four audible tracks and fixed per-track gains | Combined worker contention, audio CPU/queues, own-playback exclusion |
| Presentation | Same subscriptions through grid, focus, fullscreen, visible-unfocused, minimized, occluded when supported, then restore | Invisible conversion/upload reduction, visibility propagation, stale texture cleanup, restore time and no false fallback |
| Lifecycle soak | Repeated explicit stop/rewatch, source/codec switches, leave/rejoin/reconnect and final stop/leave; vary dimensions deliberately | Live-object/reference/handle/thread slopes, cache bounds, canceled-generation work and eventual resource release |
| Concurrent joins/server | Several synthetic clients join/rerun/cancel within existing admission limits; exercise API/proxy/SFU separately | Probe leases/chunk allocation/query count, pending retry fairness, event-loop delay, heap/external memory/GC and SFU CPU/RAM |
| Physical game | Game alone; app idle; sharing; watching one/four; sharing plus watching. Identical repeatable scenes/settings and media parameters | CPU scheduling/GPU competition and p95/p99 game frame-time regression; does not follow from synthetic throughput |

For every native case collect:

- Process-tree CPU time deltas (state whether normalized to one core or total machine), thread CPU time, context switches/wakeup rate and runnable/blocked intervals; total/active thread and handle counts. OS thread count and scheduled task count are separate. A later controlled ETW/WPA capture can investigate scheduling ([Microsoft CPU analysis][cpu-analysis]); this audit neither installed nor ran it.
- Wrapper and child **separate** working set, private working set, private bytes/process commit and peaks; system commit; allocation count/bytes/peak live bytes, including RGBA/I420/JPEG and texture-delta lifetimes. Report settle behavior and repeat-cycle slopes rather than just a peak screenshot. Do not sum shared working-set pages as unique RAM.
- GPU local/nonlocal bytes and budgets, decoder surfaces/textures/pool counts where instrumentable, encode/decode/copy/3D utilization. API-visible texture payload size is not necessarily the driver's resident VRAM charge.
- Stage timing distributions and queue high-water in **bytes, frames and wall-clock age**: decoder input/output, I420 copy, conversion, overwritten pictures, texture submission and presentation. Collect actual received/delivered and actually presented FPS separately from requested FPS and conversion counts; UI redraws are not new video frames. Record media latency, audio underruns/queue age/A/V offset, and game frame-time p50/p95/p99 with spikes and run-to-run variability.

Apply correctness gates alongside resource metrics: explicit Stop watching must end full incoming video/audio traffic after in-flight data settles; fullscreen/minimize/focus must retain the same subscriptions and audio. Count preview captures independently of uploads and enforce start/60-second cadence before GPU readback. Exercise cancellation during conversion, immediate rewatch, source/codec replacement, size change, device loss and reconnect with stale-result rejection. Keep resolution/FPS/bitrate controls explicit and one publication. Exercise Discord restart, own-playback exclusion, PID reuse and denied/unknown identity fail-closed behavior without microphone acquisition. No CPU reduction qualifies if delivered/presented FPS, A/V timing, game tails or these contracts regress.

Accept a change only after matched runs establish its intended metric with uncertainty and without sustained backlog or unacceptable regressions. Synthetic correctness/performance is the prerequisite, not a substitute for real capture, physical output or gaming. Test the supplied RTX 5080 system separately from actual AMD hardware; the RX 7600 whole-monitor HEVC 1080p120/25 Mbps/Siege report, fresh-machine portable behavior, real Discord exclusion, deployment/network limits and 4K120 remain their own physical/external acceptance gates. No such gate was completed by this research.
