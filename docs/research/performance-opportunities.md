# Further performance opportunities

Research date: 2026-11-09. Source inspection of the uncommitted working tree on `fix/windows-executable-icon`, plus current primary documentation and versioned upstream source. This report changes no application behavior. No runtime, hardware, deployment or performance verification was performed; the ordering below is an engineering recommendation, not a measured bottleneck ranking or a savings estimate.

**Implement first:** add stage/queue measurements, simplify the CPU image conversion, then make conversion and repaint work follow actual presentation demand through bounded workers. Measure that limited batch before changing decoder recovery, encoder presets or native rendering.

## Evidence and existing work

- **Observed receiver path:** [decoder configuration:24](../../apps/publisher/decoder/freedomstream_decoder.h#L24) selects D3D11 decoding followed by `d3d11download`, `videoconvert` and I420. [Receive:110](../../apps/publisher/decoder/freedomstream_decoder.h#L110) allocates a WebRTC I420 buffer and copies its planes. [Playback:443](../../apps/publisher/src/playback.rs#L443) runs conversion in a Tokio task; [lines 459 onward](../../apps/publisher/src/playback.rs#L459) allocate RGBA bytes and then a separate `ColorImage` for every received frame. GStreamer's [download documentation](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11download.html) confirms the GPU-to-system-memory boundary. Hardware decode therefore does not establish a GPU-resident presentation path.
- **Observed UI path:** [update_picture:614](../../apps/publisher/src/ui.rs#L614) takes ownership of the image; there is no image clone here to remove. [Repaint scheduling:825](../../apps/publisher/src/ui.rs#L825) polls at about 16 ms while watching and 250 ms when hidden/idle. [Fullscreen:847](../../apps/publisher/src/ui.rs#L847) renders one tile, while the independent subscribed pumps continue converting. This establishes potentially avoidable work, not its measured cost.
- **Already present:** [SDK queue capacity one:447](../../apps/publisher/src/playback.rs#L447), bounded capture/preview queues in [encoding:149](../../apps/publisher/src/encoding.rs#L149), GPU-memory publication through that pipeline, [preview gating before scaling/download:230](../../apps/publisher/src/encoding.rs#L230), the [60-second capture gate](../../apps/publisher/src/preview.rs#L11), shared adaptive encoding and [coalesced AMF changes](../../apps/publisher/src/quality.rs#L331). These are baseline work, not new recommendations. The pinned [LiveKit queue implementation](https://github.com/livekit/rust-sdks/blob/88705b15086ecbe2c26ee91ede6203f974a0fc62/libwebrtc/src/native/video_stream.rs) confirms that capacity one replaces the pending decoded frame with the latest; it does not avoid conversion of frames already taken by the consumer.

Version basis: bundled GStreamer **1.28.8+git**, with exact source commit in the [runtime manifest:2](../../deploy/portable-runtime.json#L2); `libwebrtc` **0.4.0**, `livekit` **0.10.1**, egui/epaint/ecolor/egui_glow **0.37.0**, Tokio **1.54.1** in [Cargo.lock](../../Cargo.lock#L4298). The local SDK packages identify upstream commit `88705b15086ecbe2c26ee91ede6203f974a0fc62`. GStreamer links below use 1.28.8 or the bundled commit where available; live documentation is supplementary and is not proof that every property exists in the shipped build.

## Prioritized candidates

Effort is relative implementation scope, not a time estimate. All expected benefits are hypotheses requiring the measurement plan below.

| Order | Candidate                                                                | Effort                       | Expected opportunity                                                                | Principal risk / gate                                               |
| ----- | ------------------------------------------------------------------------ | ---------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 1     | Direct CPU conversion and stable texture updates                         | Small–medium                 | Remove an intermediate buffer and per-pixel construction pass                       | Pixel/alpha correctness and image ownership                         |
| 2     | Presentation demand, bounded conversion workers and frame-driven repaint | Medium                       | Avoid converting pictures that cannot be presented; isolate CPU work from async I/O | Fairness, cancellation, false decoder-stall detection               |
| 3     | Decoder frame/age limits and keyframe-safe recovery                      | Medium                       | Bound stale playback under device stalls, including low-bitrate streams             | Breaking compressed reference chains or recovery signaling          |
| 4     | Encoder/capture adapter and pacing experiments                           | Medium + physical AMD access | Identify contention or preset tradeoffs in the reported monitor-capture case        | Image-quality regression; NVIDIA cannot qualify AMD                 |
| 5     | Shared software-AV1 CPU budget                                           | Medium–large / SDK seam      | Control aggregate decode contention while gaming                                    | Too few threads can miss deadlines; pinned settings need inspection |
| 6     | Shared audio playout with device-clock integration                       | Large / SDK seam             | Consolidate output scheduling and make actual device delay available                | A/V drift, per-track volume, unintended microphone capture          |
| 7     | Cached, event-assisted process/audio inventory                           | Medium; optional             | Reduce repeated enumeration if profiling shows material cost                        | Stale identities can violate capture exclusions                     |
| 8     | Native D3D11 texture receive/render interface                            | Very large                   | Remove CPU download/copy/conversion/upload stages where compatible                  | SDK bridge, adapter/device lifetime, synchronization and recovery   |

### 1. Simplify CPU conversion before changing renderers

**Proposal:** at [playback:459](../../apps/publisher/src/playback.rs#L459), create a correctly sized `ColorImage` and write `to_argb` output directly into `ColorImage::as_raw_mut()`. [epaint 0.37 image source](https://github.com/emilk/egui/blob/0.37.0/crates/epaint/src/image.rs) exposes that method behind `bytemuck`; [egui_glow's dependency](https://github.com/emilk/egui/blob/0.37.0/crates/egui_glow/Cargo.toml) enables the feature. This can remove the separate RGBA vector and `from_rgba_unmultiplied` construction pass, while still allocating the destination image.

First prove ABGR-to-byte ordering, full writes, stride, dimensions and opaque alpha with deterministic fixtures. [Color32](https://github.com/emilk/egui/blob/0.37.0/crates/ecolor/src/color32.rs) stores premultiplied sRGBA; direct writes are equivalent only when the output satisfies that contract. Preserve color matrix/range and the existing SDR appearance.

Reuse overwritten/unpresented images or a small pool only after exclusive ownership is recovered. Images passed to the texture system are held through `Arc`-backed deltas; blindly mutating a retained image is unsafe, and cloning it defeats the objective. See [image representation](https://github.com/emilk/egui/blob/0.37.0/crates/epaint/src/image.rs) and [texture delta ownership](https://github.com/emilk/egui/blob/0.37.0/crates/epaint/src/textures.rs).

As a separate small A/B experiment, allocate the texture once and use `set_partial([0, 0], ...)` for equal-sized full-frame replacements, reverting to `set` on size changes. [TextureHandle](https://github.com/emilk/egui/blob/0.37.0/crates/epaint/src/texture_handle.rs) distinguishes these deltas; the [glow painter](https://github.com/emilk/egui/blob/0.37.0/crates/egui_glow/src/painter.rs) uses `tex_sub_image_2d` versus `tex_image_2d`. Both still upload all pixels. This API difference does not prove a driver allocation or a speedup; test resize and same-pass initial allocation too.

### 2. Convert for presentation through a bounded worker pool

**Proposal:** keep lightweight async frame reception, but hand the newest decoded frame to a small, globally bounded set of dedicated conversion workers. Give each subscription at most one pending decoded frame, one in-flight conversion and one completed image; replace pending frames rather than accumulating jobs. Schedule visible tiles fairly, coalesce demand to presentation deadlines and stop expensive conversion/upload for tiles obscured by fullscreen or a confirmed minimized window. Continue subscriptions, audio and decode health tracking; entering fullscreen must not unsubscribe anyone or silently change publication FPS/resolution.

[Tokio's official guidance](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html) warns that CPU work without yielding can delay other futures, recommends limiting CPU parallelism, and prefers dedicated threads for persistent workers. Do not submit unbounded per-frame `spawn_blocking` tasks. Started blocking work cannot be aborted: [Pump::drop:58](../../apps/publisher/src/playback.rs#L58) would need cooperative shutdown, closed mailboxes, generation checks before/after conversion and stale-result rejection on stop/rewatch/reconnect. Release queued frame references and join workers without blocking the UI/runtime threads.

Use coalesced [egui repaint requests](https://github.com/emilk/egui/blob/0.37.0/crates/egui/src/context.rs) on a fresh presentable image and dirty statistics/state; retain timers for animations, controls and recovery. Respect display/presentation cadence so four streams do not cause four repaint loops. The current visibility check is not proof of minimization: handle native minimized/restore events, treat unknown visibility conservatively, and request fresh conversion immediately on restore.

Move received/decode liveness updates **before** presentation gating: [the six-second fallback check:346](../../apps/publisher/src/playback.rs#L346) currently depends on [last_frame updated after conversion:475](../../apps/publisher/src/playback.rs#L475). A hidden tile must not spuriously trigger shared H.264 fallback. Track received, converted, superseded and actually presented frames separately.

### 3. Bound decoder age and frame count, preserving references

**Observed:** [Decode:46](../../apps/publisher/decoder/freedomstream_decoder.h#L46) rejects an input over 4 MiB and rejects pushes when appsrc already exceeds 4 MiB. This is an existing bound with possible one-input overshoot, not an unbounded queue. Under serialized pushes the appsrc queue can reach roughly 8 MiB; parser/decoder in-flight storage is additional. The 128-entry timestamp ledger is not a decoder frame-count limit.

**Proposal:** record enqueue-to-output wall-clock age and outstanding frame count alongside bytes; use measured thresholds and a controlled recovery state. `max-bytes` with `block=false` alone is not a hard admission cap: [bundled appsrc source](https://github.com/GStreamer/gstreamer/blob/202e42fa1bbff4ed61e08d47202db5c744987f0c/subprojects/gst-plugins-base/gst-libs/gst/app/gstappsrc.c) distinguishes full-queue signaling, blocking and leaking. Retain an explicit guard. [PTS generation:56](../../apps/publisher/decoder/freedomstream_decoder.h#L56) advances by 1 ms per input, so `max-time` alone would not represent real queue age without corrected timestamp/duration semantics.

Do not add a blindly leaky compressed queue. On overrun, flush/recreate safely, invalidate the timestamp generation, request a codec-appropriate keyframe and resume at a valid random-access point with required headers. [GStreamer decoder sync-point documentation](https://gstreamer.freedesktop.org/documentation/video/gstvideodecoder.html#gst_video_decoder_request_sync_point) explicitly identifies missing reference frames as a reason to request synchronization. Its upstream event does not automatically bridge appsrc into LiveKit/WebRTC; qualify that signaling seam and bounded retries. Exercise H.264, HEVC and AV1 loss/stall/reconnect separately.

### 4. Measure encoder preset, adapter and capture pacing tradeoffs

**Observed:** [encoder setup:208](../../apps/publisher/src/encoding.rs#L208) already uses NVIDIA P4/ultra-low-latency/CBR/no B-frames and AMF low-latency modes/CBR. [Capture selection:167](../../apps/publisher/src/encoding.rs#L167) supports DXGI monitor and WGC monitor/window paths. [AMF rate changes:385](../../apps/publisher/src/encoding.rs#L385) are already coalesced; do not present that as another fix.

**Proposal:** log sanitized adapter LUIDs and stage timings, then compare AMF default/balanced/speed presets and NVIDIA P4 versus a faster supported preset at identical geometry, FPS, bitrate, source and content. [GStreamer 1.28.8 AMF source](https://github.com/GStreamer/gstreamer/blob/1.28.8/subprojects/gst-plugins-bad/sys/amfcodec/gstamfh265enc.cpp) exposes the preset choices; [AMD tuning guidance](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/wiki/AMF-Encoder-Settings-and-Tuning-in-FFmpeg) describes their quality/speed tradeoff. Its FFmpeg flags are not GStreamer property names. [NVIDIA's guide](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html) similarly distinguishes performance/quality presets.

Compare DXGI/WGC only where each captures the required source correctly. Correlate capture interval, `clocksync` wait, encoder input/output delay, reconfiguration/keyframe events, GPU copy/3D/video-engine activity and game frame-time spikes. [Capture documentation](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11screencapturesrc.html) qualifies adapter selection specifically for WGC; do not assume setting it reroutes DXGI capture. Preserve static-scene/late-join keyframes provided by [imagefreeze:140](../../apps/publisher/src/encoding.rs#L140). No preset or capture-backend change is an established RX 7600/Siege stutter fix without that physical test.

### 5. Budget software AV1 across subscriptions and the game

**Observed:** [decoder factory:149](../../apps/publisher/decoder/freedomstream_decoder.h#L149) retains the SDK dav1d fallback and supports explicitly forcing software for qualification. That does not establish four-stream CPU capacity on any machine.

**Proposal:** inspect the pinned WebRTC dav1d configuration and expose a narrow aggregate decode budget if measurements justify it. Coordinate decoder thread/frame-delay settings across streams with conversion workers and game load. [dav1d's API](https://github.com/videolan/dav1d/blob/master/include/dav1d/dav1d.h) exposes those settings; its defaults are not proof of the settings used by the compiled WebRTC decoder, nor evidence that a Rust tuning knob exists. Lowering thread counts may increase latency rather than help.

Qualify one and four software-decoded streams **while gaming**, including sustained queues and p95/p99 game frame times. Keep grain/quality semantics intact and do not infer reduced decoder pixel work from lower network bitrate. If capacity is inadequate, provide an explicit supported choice; preserve watch intent and the single shared publication's existing compatibility contract. The [AV1 hardware research](av1-hardware.md) supplies capability context, not a throughput certificate.

### 6. Evaluate one playout device and a real clock/delay contract

**Observed:** [audio:566](../../apps/publisher/src/playback.rs#L566) builds one GStreamer/WASAPI pipeline per track. It already has a five-frame SDK queue, a 38,400-byte appsrc threshold with [explicit pre-push guard:625](../../apps/publisher/src/playback.rs#L625), and a downstream queue capped at approximately 100 ms. The appsrc threshold corresponds to 200 ms of stereo S16/48 kHz PCM by arithmetic; it is not measured device latency or the total pipeline delay. [Phase 12's timing investigation](../verification/phase-12.md#audio-timing-investigation) records that output device delay is not returned to WebRTC and physical A/V offset remains unverified.

**Proposal:** compare a shared mixer/output sink against a playout-only SDK/ADM integration with per-track gain and actual device-delay feedback. A mixer alone does not repair synchronization. [IAudioClock](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-iaudioclock) provides device position/rate; [GetStreamLatency](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getstreamlatency) reports maximum stream latency, not an instantaneous speaker deadline. Account for queued samples and clock mapping too.

Do not directly adopt [PlatformAudio::new](https://github.com/livekit/rust-sdks/blob/88705b15086ecbe2c26ee91ede6203f974a0fc62/livekit/src/platform_audio/mod.rs): this pinned implementation enables recording as well as playout, while the [Rust audio-track interface](https://github.com/livekit/rust-sdks/blob/88705b15086ecbe2c26ee91ede6203f974a0fc62/libwebrtc/src/audio_track.rs) lacks the needed per-track volume control. Require a room-runtime-owned, playout-only seam, stereo gain/mute isolation, hotplug/reconnect handling, and continued own-playback/Discord exclusion with no microphone acquisition. Do not add an arbitrary constant video delay or claim the lag fixed before physical tests.

### 7. Cache inventories only with unchanged fail-closed policy

**Observed:** [capture refresh:218](../../apps/publisher/src/audio/mod.rs#L218) refreshes process/audio inventory twice per second. [Inventory:67](../../apps/publisher/src/audio/windows.rs#L67) enumerates processes, opens identity/image handles, then walks active render devices/sessions. Its cost has not been measured.

**Proposal:** if profiling makes this worthwhile, share an identity cache and invalidate it using process/session/device events, with reconciliation and the current polling fallback. [Windows session notifications](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nn-audiopolicy-iaudiosessionnotification) require correct MTA initialization and careful session-list maintenance; [endpoint notifications](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient) cover device changes. [Process-start events](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/krnlprov/win32-processstarttrace) are an invalidation hint, not authoritative process identity or a guaranteed permission-free replacement.

Preserve [PID plus creation time and parent birth ordering:24](../../apps/publisher/src/audio/policy.rs#L24), image identity, protected descendants and [unknown-identity rejection:106](../../apps/publisher/src/audio/policy.rs#L106). An ambiguous event, overflow, access failure or uncertain descendant state must trigger safe revalidation/omission, never temporary broad desktop capture. Do not lengthen the exclusion-detection window merely to save polling. Keep this optional until its cost and security-equivalent behavior are established.

### 8. Design a native texture receive/render seam if copies dominate

**Proposal:** preserve decoded NV12 D3D11 surfaces through the decoder callback, SDK bridge and renderer, performing required color conversion on the GPU. [D3D11 H.265 output caps](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11h265dec.html) and [d3d11convert](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11convert.html) establish the upstream building blocks. [GStreamer 1.28.8 memory interfaces](https://github.com/GStreamer/gstreamer/blob/1.28.8/subprojects/gst-plugins-bad/gst-libs/gst/d3d11/gstd3d11memory.h) distinguish native-resource mapping from system memory. This is a substantial replacement for [Receive:97](../../apps/publisher/decoder/freedomstream_decoder.h#L97), not a pipeline-string tweak.

The pinned [LiveKit native-buffer interface](https://github.com/livekit/rust-sdks/blob/88705b15086ecbe2c26ee91ede6203f974a0fc62/libwebrtc/src/video_frame.rs) exposes Apple/Linux native paths but no corresponding public Windows D3D11 texture import/export API; the app currently uses glow. Merely switching eframe to WGPU leaves the decoder's I420 download/copy path intact.

Require explicit adapter/device ownership, surface-pool and frame lifetimes, bounded texture retention, NV12 plane/color handling, safe synchronization, resize/device loss and reconnect generations, plus the CPU fallback. Shared resources need a defined synchronization protocol: Microsoft's [keyed-mutex contract](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgikeyedmutex-acquiresync) includes timeout and abandoned-resource recovery. Do not assume all surfaces are shareable or cross-adapter imports free. Qualify NVIDIA and AMD independently and review dependency/runtime licenses before bundling anything new. Accept this project only after stage measurements justify its scope.

## Measurement and implementation sequence

1. **Establish a sanitized baseline.** Add monotonic local timestamps/counters around capture, encode submit/output, decoder submit/output, I420 copy, RGBA conversion, pending-image replacement, texture upload and presentation. Record queue high-water in bytes, frames and wall-clock age, plus drops by stage/reason. Separate actual decode/receive health from presentation. The [GStreamer latency tracer](https://gstreamer.freedesktop.org/documentation/coretracers/latency.html) supports pipeline, element and reported latency; it does not cross the SFU or measure physical display/audio output. Use synthetic fixture pipelines and sanitized aggregate exports, without raw signaling/network logs, credentials, invitations or process paths. [GPUView guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/using-gpuview) can inform a later narrowly scoped GPU/CPU scheduling investigation; no tracing, installation or privilege changes were performed for this report.
2. **Implement only candidates 1 and 2 initially.** Validate deterministic color/stride/alpha and changing dimensions; overload conversion deliberately; assert bounded pending work, fair service and stale-generation rejection. Exercise Stop watching, immediate rewatch, leave/rejoin, codec/source switches and reconnect while work is queued. Confirm async signaling/audio/control responsiveness and shutdown. Compare direct conversion and partial texture updates independently so each result is attributable. Pool reuse remains conditional on ownership evidence.
3. **Run actual synthetic media before physical claims.** Use known-size motion patterns, a static scene for late-join keyframes, and the existing [flash/click source](../verification/av-sync-fixture.md). Test H.264/HEVC/AV1 hardware paths and explicitly forced software AV1, with **one and four actual subscriptions**. Cover grid, focused layout, fullscreen, visible-but-unfocused, hidden/minimized and restore. Confirm other subscriptions/audio persist through fullscreen; obsolete presentation work decreases without a false codec fallback. Add stalls/loss and byte/frame/age high-water checks before accepting candidate 3. Compilation and mocks cannot establish media throughput.
4. **Qualify physical game impact separately.** Available local hardware is the task-supplied **Ryzen 7 9800X3D / RTX 5080**. Compare game-only, publishing-only, watching-only and publishing plus one/four watched streams, with identical repeatable game scenes/settings, source geometry/FPS/bitrate, driver, display refresh, power/thermal state and recording method. Use warm-up, repeated comparable runs and sustained sessions; report game frame-time **p50/p95/p99**, spikes, delivered/presented FPS, stage latency distributions, CPU/thread/memory use, GPU encode/decode/copy/3D activity and queue high-water. Start at 1080p60, then qualify 1080p120, 1440p60 and 4K modes explicitly. Offered settings or vendor capability tables do not qualify 4K120. Repeat the reported **RX 7600 whole-monitor HEVC 1080p120 / 25 Mbps Siege** case on actual AMD hardware; that gate is unavailable locally and remains open.
5. **Verify physical A/V timing and product invariants.** Observe the fixture at the actual display and wired output, with a local-playback reference and known measurement uncertainty. Record offset/variance at startup and after sustained playback, plus switches/reconnect and one/four tracks. Queue counters are not speaker latency. Exercise per-track gain/mute, device changes, Discord restarts, PID reuse, denied identity access and watched-stream feedback exclusion. Separately measure actual incoming media-byte deltas before/after **Stop watching** after in-flight traffic settles, distinguishing media from room signaling. Hiding/fullscreen must retain the subscription; explicit stop must end it. Count real preview captures and uploads: one on start and no subsequent capture less than 60 seconds later; joining, focus, reconnect and network retries must not accelerate capture.

**Conditional SFU/network work:** retain the existing [receiver headroom budget:74](../../apps/publisher/src/network.rs#L74). Measure server ingress/egress, packet rate, CPU/RAM, loss/retransmissions, TURN/TLS use and competing workloads under the intended four/five-publisher subscription graph. Plan egress as the sum of delivered publisher bitrate times actual subscribers, plus audio/transport/retransmission overhead, against the documented 1 Gbps port; do not infer remaining capacity from a capped connect-time test. [LiveKit's benchmark guidance](https://docs.livekit.io/transport/self-hosting/benchmark/) uses workload-specific tests and different server hardware, not a guarantee for this VPS. Investigate load/probe admission and host/network capacity only when telemetry points there. Dual encoding, SFU transcoding, hidden unsubscribe and silent geometry/FPS reductions are outside these recommendations.

Retain a change only if the matched before/after runs improve its intended metric without worse game tails, latency drift, sustained backlog, media correctness or subscription/exclusion behavior. Report uncertainty and unavailable hardware explicitly. The report establishes source-backed opportunities; it establishes no achieved speedup, AMD fix, synchronized-playback fix or end-to-end throughput claim.
